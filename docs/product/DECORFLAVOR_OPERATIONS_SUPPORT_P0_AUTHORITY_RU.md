# DecorFlavor — Operations & Support P0

**Статус:** ACTIVE — owner-authorized 18 августа 2026 года  
**Уровень проектирования:** 2  
**Зависимость:** расширяет, но не изменяет денежные границы `DECORFLAVOR_MANUAL_INVOICE_P0_AUTHORITY_RU.md`.

## 1. Бизнес-результат

После создания заказа команда должна видеть, какой заказ требует действия, а покупатель — получать понятный статус и иметь безопасный канал обращения в поддержку. Это завершает операционный контур вокруг заказа со счётом, выставленным продавцом вне DecorFlavor.

## 2. Подтверждённое состояние

- P0-заказ, роли buyer/seller/platform admin, audit log, outbox и персональные in-app notifications уже существуют.
- Заказ проходит состояния `AWAITING_SELLER_INVOICE → INVOICE_SENT → PAYMENT_VERIFICATION_PENDING → PAYMENT_CONFIRMED → READY_FOR_FULFILLMENT`; до подтверждения оплаты доступна отмена.
- Платёжные данные, платёжные ссылки, реквизиты, документы и внешние платёжные API не хранятся и не вызываются.
- У платформы уже есть экран очереди подтверждения оплаты и экран персональных уведомлений; автоматическая генерация уведомлений для order-flow отсутствует.

## 3. Scope текущего среза

1. Создавать **in-app** уведомления для buyer, уполномоченных сотрудников seller и платформенных операторов при значимых переходах заказа.
2. Добавить безопасные фильтры и сигналы внимания в seller/admin queue: статус, текстовый поиск, просроченный внешний счёт и ожидающее подтверждение оплаты.
3. Добавить привязанное к заказу обращение в поддержку:
   - buyer создаёт обращение только по своему заказу;
   - platform support/admin переводит его в работу или решает, оставляя видимый покупателю комментарий;
   - buyer видит только собственные обращения и их историю;
   - seller не получает доступ к содержанию обращения.
4. Фиксировать изменения обращения и уведомления в audit/outbox той же транзакцией.
5. Добавить API/integration tests и технический production-readiness runbook без публикации приложения.

## 4. Вне scope

- Email, SMS, мессенджеры, почтовый провайдер и любые реальные внешние отправки.
- Приём денег, реквизиты, payment link, чек, банковская выписка, invoice PDF, webhook, escrow, payout или refund.
- Доставка, адрес, маршрут, водитель, POD/фото и settlement с перевозчиком.
- Вложения к обращениям, платёжные доказательства, спор/чарджбек, юридическое решение по возврату.
- Реальный production deploy, DNS/домен, production database, секреты, юридические документы и налоговая конфигурация.

## 5. Канонические термины

| Термин | Значение |
| --- | --- |
| **Operational notification** | Доставленное внутри приложения событие; оно не означает email/SMS и не передаёт деньги. |
| **Attention signal** | Вычисляемый признак очереди: просрочен внешний счёт либо заказ ожидает ручного решения платформы. |
| **Support case** | Приватное обращение buyer по одному своему заказу. Оно не является спором, возвратом или платёжным доказательством. |
| **Support resolution** | Видимый buyer комментарий platform support, завершающий обращение в статусе `RESOLVED`. |

## 6. Решения владельца

- **DEC-OPS-001:** канал уведомлений текущего среза — только `IN_APP`; внешняя доставка отложена.
- **DEC-OPS-002:** обращение поддержки приватно между buyer и platform support. Seller не читает его содержимое.
- **DEC-OPS-003:** P0 support не разрешает деньги, возвраты или доставку; он фиксирует запрос и операционную коммуникацию.
- **DEC-OPS-004:** production-ready означает готовность к управляемому развёртыванию по runbook, а не фактический публичный запуск.

## 7. Роли и авторизация

| Действие | Кто |
| --- | --- |
| Читать собственные уведомления и обращения | Авторизованный recipient / buyer-owner |
| Создать support case | Buyer-owner заказа |
| Читать все обращения | Platform role с `support:read` или `platform:admin` |
| Перевести обращение в работу / решить | Platform role с `support:manage` или `platform:admin` |
| Читать support case как seller | Запрещено |

## 8. Состояния

```text
OPEN -> IN_REVIEW -> RESOLVED
OPEN ----------------> RESOLVED
```

`RESOLVED` — терминальное состояние этого среза. Новый вопрос создаёт новое обращение; повторное открытие, dispute и refund находятся вне scope.

## 9. Основные сценарии

1. Seller фиксирует внешний счёт → buyer получает in-app уведомление.
2. Buyer сообщает об оплате → platform verification queue получает сигнал; seller видит обновление.
3. Platform admin подтверждает/отклоняет сообщение → buyer и seller получают статус, но никакие деньги не обрабатываются.
4. Buyer открывает support case по своему заказу → platform support получает уведомление и видит заявку в очереди.
5. Support переводит заявку в работу или решает её с комментарием → buyer видит новый статус/комментарий и уведомление.

## 10. Критические негативные сценарии

- Нельзя создать case по чужому order или читать чужой case.
- Seller не может увидеть содержимое buyer-support case.
- Нельзя изменить resolved case или выполнить недопустимый переход состояния.
- Повторная/устаревшая версия обновления не создаёт второй event, audit или notification.
- Просрочка счёта — только операционный сигнал; она не отменяет заказ и не подтверждает/отклоняет платёж.
- Никакое уведомление не создаёт email/SMS, внешнего HTTP-вызова или платёжного действия.

## 11. Граница архитектуры

- `OrderService` создаёт order outbox event и связанные in-app notifications в одной транзакции.
- `SupportCaseService` владеет authorisation, состоянием cases, audit/outbox и support notifications.
- `NotificationService` предоставляет recipient-only read model.
- Portal/Web отображают API state; принятие решений остаётся на сервере.

## 12. Контракт проверки

- Unit tests покрывают разрешённые и запрещённые переходы support state machine.
- Изолированный Postgres integration test подтверждает recipient/tenant boundaries, notifications, audit и outbox.
- Typecheck/lint и production build API, portal и web проходят.
- Runbook содержит проверяемые preflight/rollback steps и прямо перечисляет непокрытые owner decisions.

## 13. Отложенные owner decisions

1. География продаж, налоговый контур, merchant-of-record и правила возвратов.
2. Поставщик email/SMS, шаблоны, consent, deliverability и retention.
3. Production cloud, домен, доступы, backup RPO/RTO, monitoring owner и incident escalation.
4. Полный delivery/dispute/refund flow после выбора политики и операционного владельца.

## 14. Следующий разрешённый вертикальный срез

После приёмки этого среза — исполнение заказа: delivery details, назначение исполнителя и подтверждение выполнения, только после отдельного решения по PII, географии и правилам инцидентов.
